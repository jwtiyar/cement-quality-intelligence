# Improving the 2-day to 28-day strength estimate

Research checked 2026-09-22. This is an experiment order, not evidence that XGBoost already predicts accurately. Keep the current recent-average fallback until an out-of-time comparison proves otherwise. The product requires 2-day and 28-day results; it does not need 3-day or 7-day inputs.

## What the current code does

`data_prep.py` maps `Strength_Early` to `Strength_2D`, merges the three historical 28-day headers, records the source column, and excludes 2019 from ML. `ml_train.py` trains on six oxides, 2-day strength, and fineness. `ml_evaluation.py` uses expanding chronological folds and only admits historical labels available by the first prediction time in each fold. It compares XGBoost with a recent-100-record mean, Ridge, and other XGBoost variants. Production promotion requires at least three folds, wins in at least 75% of them, at least 5% lower aggregate MAE than the recent mean, and R² above 0.25. These are code observations, not proof that the inputs explain future strength.

## Recommended experiments, in order

1. **Audit labels before tuning.** By cement type, year, workbook/sheet/28-day source column, count rows and plot 28-day mean, spread, missingness, and the relation to 2-day strength. Review duplicate samples, impossible values, and changes in test procedure with plant staff. Resolve the reason for the 2019 exclusion and any source-specific offsets before merging or dropping more data. Google's tabular-data guidance notes that erroneous or missing values reduce model quality and that the meaning and availability of every feature must be checked. [Google Cloud tabular-data guidance](https://docs.cloud.google.com/vertex-ai/docs/tabular-data/tabular101).

2. **Reproduce the decision time in validation.** For each held-out sample, use only features known by its 2-day prediction time and training labels actually reported by then; when no report timestamp exists, use the documented 28-day proxy. Test each model and baseline on identical held-out samples. Use calendar periods rather than assuming a fixed number of rows equals a fixed duration, since scikit-learn cautions that its row-gap `TimeSeriesSplit` gives comparable durations only for equally spaced samples. Keep feature selection and any preprocessing inside training folds. [scikit-learn TimeSeriesSplit](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html); [scikit-learn data-leakage guidance](https://scikit-learn.org/stable/common_pitfalls.html).

3. **Measure whether chemistry adds predictive value.** On the same chronological folds, compare recent mean, training mean/median, 2-day-only Ridge, 2-day-plus-chemistry Ridge, and XGBoost using MAE in MPa, RMSE, and R². Report errors separately by cement type and time period; inspect large misses and held-out permutation importance. If the chemistry models do not beat 2-day-only and recent-mean references, adding model complexity is not justified. `DummyRegressor` documents mean and median references; permutation importance can be calculated on held-out data. [scikit-learn DummyRegressor](https://scikit-learn.org/stable/modules/generated/sklearn.dummy.DummyRegressor.html); [scikit-learn permutation importance](https://scikit-learn.org/stable/modules/generated/sklearn.inspection.permutation_importance.html).

4. **Tune conservatively only after the data audit.** Try a small, predeclared search over tree depth, minimum child weight, regularization, and sampling. Use an inner chronological validation period for XGBoost early stopping; keep the final period untouched for the model-versus-baseline decision. XGBoost's sklearn interface requires a validation `eval_set` for early stopping, and its tuning guide identifies depth, child weight, gamma, row sampling, and column sampling as overfitting controls. [XGBoost sklearn API](https://xgboost.readthedocs.io/en/stable/python/python_api.html); [XGBoost tuning guide](https://xgboost.readthedocs.io/en/stable/tutorials/param_tuning.html).

5. **Check prospective behavior before promotion.** Save each real 2-day prediction, input values, model version, and eventual 28-day result. Compare rolling MAE and large misses with the baseline after labels mature; audit whether input distributions differ from training. A passing historical score does not establish stable future performance. Google's model guidance defines training-serving skew as a mismatch between training and serving inputs. [Google Cloud tabular-data guidance](https://docs.cloud.google.com/vertex-ai/docs/tabular-data/tabular101).

## Decision

The first deliverable should be a per-type, per-era, per-source validation report with paired errors for the baseline and candidate models. Only promote an input-sensitive model if it improves those out-of-time errors consistently and the gains survive a separate, later holdout. No particular XGBoost setting can guarantee correct strength estimates when the measured inputs do not carry stable signal.
